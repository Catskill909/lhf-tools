Internal — not for client

LHF Podcast Archive — Build Plan

Working plan for the podcast search engine. Stack: Python + FastAPI, SQLite/FTS5, Docker, Coolify. Companion to the client-facing planning memo.

Read this first — the plan below was overtaken by events

This document was written before we discovered that the feeds already publish transcripts in the Podcast 2.0 <podcast:transcript> namespace. 144 of 200 episodes carry one, free. That removed most of the transcription problem this plan spends its first half solving, and cut the projected cost from ~$102 to ~$9.52 for the remaining gap.

What actually got built: ingest, transcripts, deterministic enrichment, full-text search, the interface, spreadsheet export and a lossless browser-side clip editor — with no AI and no Google Cloud account. The AI extraction pass for topics and un-hyperlinked guests is now written and wired end to end but never run — measured at $4.35 for the whole archive and about 2¢ per new episode. It needs a client decision, a key, and an admin screen to run it from; see docs/ai-layer.md.

The costing sections are kept because they remain the right analysis if the 55 untranscribed episodes or the pre-feed backlog ever need doing. Treat the phase list as history, not as a to-do list — HANDOFF.md is the current state.

Decide this first

Google API vs. grinding it out on the VPS

Worth taking seriously, because this workload is unusually well suited to self-hosting: a one-time backfill with no deadline, then a trickle of two episodes a week. Nothing about it needs to be fast.

The arithmetic

Assume ~300 episodes per show — 425 hours of audio all in. Running Whisper large-v3-turbo through faster-whisper with int8 quantization, the backfill takes:

Throughput on CPUBackfill elapsedWeekly upkeep after
1× realtime (pessimistic)~18 days~85 min
2× realtime~9 days~43 min
4× realtime~4.5 days~21 min

The useful thing about that table is that every row is acceptable. Even the pessimistic case is under three weeks of unattended background processing for a project with no launch date, and steady state is well under an hour of CPU a week forever. The conclusion doesn't depend on nailing the throughput estimate, which is good, because published CPU benchmarks are vague — turbo int8 is documented at roughly 7× faster than large-v3 and needing ~1.5 GB of RAM, but real-world rate depends on core count. Measure it in the spike.

What self-hosting wins

  • It removes the only cost in the client memo. The transcription line item goes to zero. For a nonprofit at volunteer rate, "this costs nothing to run" is a materially better story than "$102, one time."
  • Word-level timestamps, natively. Whisper emits them; this is exactly what chirp_3 can't do. Self-hosting solves the deep-linking problem outright rather than working around it — see the model table below for what we'd otherwise be stuck with.
  • The entire Google setup disappears. No service account, no JSON key to protect, no GCS bucket, no region-matching footgun, no billing account. That's a real reduction in moving parts and in things that can silently break in two years.
  • Nothing leaves the box. Not a serious concern for a public radio archive, but never a downside.

What it costs

  • Elapsed time — days, not minutes. Irrelevant here, but it does mean the backfill has to be resumable and genuinely unattended.
  • CPU contention. If this shares a box with other Coolify projects, pegging every core for a week is antisocial. Run one or two workers under nice, or cap it with cgroup limits, and it becomes invisible.
  • No diarization out of the box. Whisper doesn't do speaker labels; that needs pyannote.audio bolted on, with its own model downloads and a lot more compute. Given diarization was a Tier 4 nicety, dropping it from Tier 3 costs nothing we promised.
  • Model size is not optional. The whole product hinges on proper nouns — guest names, union locals, historical figures. Small Whisper models mangle exactly those. This has to run large-v3-turbo or better; small would be a false economy.
  • RAM headroom. ~1.5 GB for the model plus overhead, so the earlier "512 MB is comfortable" sizing applies only to the web side. The transcription worker wants a few GB while it's running.
Decision — API, not self-hosting

Both are viable, and the API wins on the thing that actually matters here: it keeps the server trivial forever. Transcription is a one-time job, so paying ~$100 once to avoid a three-week grind, a resumable-worker babysitting problem, CPU contention with every other project on the box, and a 1.5 GB model volume is a straightforwardly good trade. The self-hosted path above stays documented as the fallback if API cost ever becomes a real constraint — at this scale it isn't.

The one thing self-hosting bought us was word-level timestamps. Losing them costs less than it looks: chirp_3 still returns segment-level offsets, which lands a listener within a chunk of speech. Nobody scrubbing a labor-history podcast needs word precision to find a story.

The part nobody had priced

The second pass — AI making sense of it all

This is the step that turns a pile of transcripts into something searchable: one more API pass where a language model reads each episode's feed metadata and its transcript together, and writes out structured facts — guests, hosts, organizations, topics, a summary, notable segments. Also one-time, also just API calls, and it's the cheapest part of the whole build.

The arithmetic

Speech runs about 150 words per minute, so 425 hours of audio is roughly 3.8 million words — call it 5.1 million tokens across the full archive, or about 8,500 tokens per episode. That's small enough that each episode is a single API call: whole transcript in, structured JSON out, no chunking, no stitching, no context-window juggling.

One-time cost to run the full archive through a second AI pass
ModelStandardBatch API (50% off)
Claude Haiku 4.5~$7~$3.50
Claude Sonnet 5~$20~$10

Use the Batch API for the backfill. It's half price, and its only tradeoff — results come back within 24 hours instead of instantly — is irrelevant for a one-time job on a decades-old archive. This is close to the textbook use case for it. New episodes going forward run through the normal API since there are only two a week.

Why this shape is right

What you've described is precomputing the intelligence once at ingest and serving it with plain SQL — and that's the architectural reason Tier 3 is the smart stopping point rather than a compromise. The AI runs twice per episode, ever: once to hear it, once to understand it. Everything after that is rows in a table. The server does no inference at query time, holds no model in memory, and needs no GPU — a search is just an indexed lookup, as fast and cheap as any ordinary database query.

That's most of Tier 4's feel — browse by guest, by topic, by theme, with AI-written summaries — at Tier 3's operating cost. True Tier 4 (semantic search over embeddings) is the version that puts a model back in the query path, and it's the one you can genuinely defer forever.

Bandwidth, since you raised it

You're right that it's not much. Podcast MP3s run 64–128 kbps, so the full archive is roughly 12–24 GB to pull from Podbean, plus the same again pushing it to Google Cloud Storage. Call it 25–50 GB of transfer, one time. Contabo's entry tier includes unlimited traffic at 200 Mbit/s — this is a rounding error, and it's the only bandwidth-heavy thing the project ever does.

Fallback path

If we do go with Google

Google's two current Chirp models each support exactly one of the two things we want, and not the other. This isn't a config flag — it's a model choice, and it determines what Tier 3 can actually promise.

ModelWord timestampsDiarizationAvailability
chirp_3 Not supported Yes — BatchRecognize only us / eu multi-region, GA
chirp_2 Yes — opt-in Not supported us-central1, europe-west4, asia-southeast1 — Private GA
Only bites on this path

The memo's Tier 3 says you can "jump straight to that timestamp." With chirp_3 that's only true at segment granularity — each result carries an end offset, so we can land the listener within a chunk of speech, not on the exact word. Probably fine for a podcast; nobody needs word-precision to find a story. But it's a constraint we simply don't have if we self-host, which is a decent part of why self-hosting is leading.

If Google, then chirp_3. It's plain GA with no access request, it's the accuracy story, and diarization is a real bonus. chirp_2 is Private GA — an access request and a dependency on Google's approval timeline, which is a bad thing to put on the critical path of a project nobody is being paid much for.

Sizing

Will the cheapest Contabo box do it?

Their entry tier is Cloud VPS 4 — 4 vCPU, 8 GB RAM, 100 GB SSD, €5.50/mo on a 24-month term. Against what this workload actually needs:

ResourceAvailableNeededVerdict
RAM8 GB~2 GB model + ~1 GB app/OSAmple headroom
Storage100 GB SSD1.5 GB model, <100 MB transcripts, one MP3 at a timeNot close to a constraint
vCPU4 (shared)The whole job — it's CPU-boundWorkable, see below

RAM was the thing that could have ruled it out and 8 GB isn't remotely close to a limit. Transcripts are just text — 425 hours of speech lands somewhere under 100 MB. Storage is a non-issue.

The caveat

Contabo's Core VPS line is oversubscribed shared vCPU, and their own page describes it as running "across multiple CPU generations" — the AMD EPYC and NVMe hardware is explicitly the Performance tier, not this one. So these are likely older cores with variable noisy-neighbour throughput, and int8 inference speed depends heavily on CPU vector instructions (AVX-512/VNNI roughly doubles int8 throughput and is not guaranteed on older silicon). Derate accordingly: plan for the 1–2× realtime end of the range, i.e. a 9–18 day backfill using most of the box. Fine for an unattended job with no deadline; not fine if you were expecting it in an afternoon.

If this box also runs your other Coolify projects, capping the worker at 2 of 4 cores pushes the backfill toward 3+ weeks. At that point the VPS 6 (6 vCPU / 12 GB, €7.50) is worth €2/mo to keep everything else responsive while it grinds.

With the API decision, this stops mattering

Everything above assumes the VPS is doing the transcription. Going through Google instead, the box never runs a model at all — it downloads files, makes API calls, and writes rows. The vCPU column stops being a constraint entirely, and the €5.50 tier is comfortably oversized for what's left: a small search API and a weekly cron job. 8 GB of RAM for a SQLite-backed search app is luxurious.

Keep the self-hosted numbers on file anyway — they're the fallback if API cost ever changes, and they're the reason we can say the fallback is real.

Adding it to the existing Coolify box

This lands on the existing VPS alongside everything else already running there. Its real steady-state footprint:

ResourceSteady stateDuring backfill
RAM~200–400 MB (FastAPI + SQLite)Same — no model in memory
CPUIdle except when someone searchesNear-idle — the work is I/O, not compute
Disk~200–300 MB (database + transcripts, all text)+ scratch for audio in flight — prune after each episode
NetworkNegligible25–50 GB total, one time

Steady state, it's quieter than most web services — a search is an indexed SQLite lookup. The backfill is the only period it's doing anything noticeable, and even then it's waiting on network rather than burning CPU.

The one real risk on a shared box

Don't let the backfill saturate the network port. A naive worker that fires parallel downloads and GCS uploads can eat the box's entire uplink for hours, and every other service on it — anything making outbound API calls, pulling images, or serving traffic — gets slow at the same time. That's the failure mode most likely to make this project annoying to a neighbour, not CPU or RAM.

Fix it up front: process episodes serially, or two at a time at most, and put a small sleep between them. There's no deadline — a backfill that takes four days instead of one costs nothing and stays invisible to everything else on the box. Cap the worker in Coolify's resource limits as belt-and-braces.

Pre-flight checks

df -h                    # free disk — 20 services + Docker images add up
free -h                  # RAM headroom; we need ~400 MB
docker system df         # reclaimable image/layer cruft if disk is tight

Then two things worth settling before the backfill rather than after:

  • Scratch-space discipline. Delete each MP3 immediately after its transcription returns. Skip that and a 600-episode backfill quietly writes ~20 GB of audio onto a disk shared with 20 other services.
  • Off-box backup of the SQLite file. More important now than on a dedicated box: one machine holds 20 projects, and this one contains transcripts that cost real money and days of wall-clock to regenerate. The feeds are re-scrapeable for free; the transcripts are not. A nightly copy somewhere off the VPS is cheap insurance.
Fallback path

Local Whisper setup

Kept documented in case API cost ever becomes a constraint. Almost nothing to set up — no accounts, no keys, no billing.

pip install faster-whisper

# first run downloads the model (~1.5 GB) and caches it
python - <<'PY'
from faster_whisper import WhisperModel
m = WhisperModel("large-v3-turbo", device="cpu", compute_type="int8")
segments, info = m.transcribe("ep.mp3", word_timestamps=True)
for s in segments:
    print(f"[{s.start:7.2f} → {s.end:7.2f}] {s.text}")
PY

Time that against the episode's known duration and you have the realtime factor the whole schedule depends on. Cache the model into a named Docker volume so it isn't re-downloaded on every deploy — that's the one deployment detail worth getting right early.

Memory jog — primary path

Google Cloud setup, start to finish

The setup we'll actually be doing. Walked out in full so it isn't a research project on the day.

The thing that trips everyone up

Speech-to-Text does not authenticate with a plain API key. You need a service account and its JSON key file (or ADC). If you go hunting for "create API key" you'll find one, it won't work for STT, and the error message won't be obvious about why.

Second thing worth knowing up front: BatchRecognize can't read audio over plain HTTP. Input has to be a gs:// URI, so a Cloud Storage bucket isn't optional — the worker downloads the MP3 from Podbean, uploads it to GCS, then points the API at it.

Console steps

  1. Create the project. console.cloud.google.com → project picker (top bar) → New Project. Name it something like lhf-podcast-archive. Note the project ID — it's what the API wants, and it's often not identical to the display name.
  2. Attach billing. Billing → link an account. The API returns 403 without it even inside the free tier. New accounts get $300 credit, and STT includes 60 free minutes/month, so the backfill may cost literally nothing.
  3. Enable two APIs. APIs & Services → Enable APIs and Services → enable Cloud Speech-to-Text API and Cloud Storage API. Missing the Storage one is an easy way to lose twenty minutes.
  4. Create the bucket. Cloud Storage → Create. Give it a region consistent with the model location you use (us multi-region pairs with chirp_3 in us). Two folders by convention: audio/ for uploads, transcripts/ for the JSON that comes back. Set a lifecycle rule to delete audio/ objects after ~7 days — we don't need to warehouse the MP3s, and it keeps storage cost at effectively zero.
  5. Create the service account. IAM & Admin → Service Accounts → Create. Name: stt-worker. Grant it roles/speech.client and roles/storage.objectAdmin (scope the storage role to just this bucket if you want to be tidy about it).
  6. Download the key. Open the service account → Keys tab → Add Key → Create new key → JSON. It downloads once and Google keeps no copy. Put it somewhere sane immediately and never let it near the repo.
  7. Wire it into the app. Mount the JSON into the container and point GOOGLE_APPLICATION_CREDENTIALS at its path. The Google client libraries pick it up automatically — no code needed to load it.
Possible snag

If Create new key is greyed out, an org policy (iam.disableServiceAccountKeyCreation) is blocking it. That's common on managed/work Google Workspace accounts and won't apply to a personal one — but if it bites, the fix is either a policy exception or Workload Identity Federation, which is a much bigger lift for a self-hosted box.

Smoke test before writing any app code

# authenticate locally as the service account
export GOOGLE_APPLICATION_CREDENTIALS=~/.secrets/lhf-stt.json
gcloud auth activate-service-account --key-file=$GOOGLE_APPLICATION_CREDENTIALS
gcloud config set project YOUR_PROJECT_ID

# put one real episode in the bucket
curl -sL -o ep.mp3 "https://.mp3"
gsutil cp ep.mp3 gs://lhf-podcast-archive/audio/ep.mp3

# confirm the API answers at all
gcloud ml speech recognize-long-running \
  gs://lhf-podcast-archive/audio/ep.mp3 \
  --language-code=en-US --async

If that returns an operation name, auth, billing, API enablement, and bucket permissions are all correct — which is the entire class of setup problems out of the way in one command. The real pipeline then uses the v2 BatchRecognize endpoint rather than this gcloud convenience wrapper.

Region footgun

In Speech-to-Text v2, three things have to agree: the recognizer location in the resource path, the API endpoint host, and (practically) the bucket region. A non-global location needs the matching regional host — e.g. us-speech.googleapis.com with projects/PROJECT/locations/us/recognizers/_. Mismatch these and you get a confusing not-found on the recognizer rather than a clear region error. No recognizer resource needs creating, by the way — _ is a valid implicit recognizer, config goes inline in the request.

Shape of it

Data model

One SQLite file. Normalized tables for the things we filter on, plus an FTS5 virtual table for everything we search. Episodes key off the RSS <guid>, which is stable across Podbean edits — never off title or URL.

episodes      id, show_id, guid UNIQUE, title, published_at,
              duration_sec, audio_url, episode_url,
              description_html, description_text,
              transcript_status, transcript_text, extracted_at

shows         id, name, feed_url, slug

people        id, name, normalized_name UNIQUE, bio_url
episode_people  episode_id, person_id, role   -- guest | host | interviewer

topics        id, name, normalized_name UNIQUE
episode_topics  episode_id, topic_id

segments      id, episode_id, start_sec, end_sec, speaker_tag, text
              -- transcript chunks; powers deep-linking + diarization

episode_notes id, episode_id, body, replayed_at   -- internal "in the can" tracking

episodes_fts  -- FTS5: title, description_text, transcript_text, people, topics

normalized_name is the deduplication hook — lowercase, strip punctuation and honorifics — so "Dr. Jeffrey Johnson", "Jeffrey Johnson" and "jeff johnson" collapse to one person record instead of three. This is the single most important thing for the catalog to feel correct, and it's where an AI extraction pass will otherwise happily make a mess.

Sequence

Phases

0

Spike — de-risk the two unknowns — superseded

half a day

Before building anything structural, answer the three questions that could invalidate the plan:

  • Run one episode end to end through chirp_3. Confirm the result objects carry usable segment offsets and that diarization tags come back. This is the deep-linking promise, tested.
  • Read that transcript for proper nouns. Not overall accuracy — specifically whether it gets guest names, union names, and historical figures right. That's the product.
  • Test extraction on ~20 real descriptions from both feeds and eyeball the guest/topic output. Show notes vary a lot in format; better to know now than after building a UI on top of it.

Also worth doing here: paginate the full Podbean archive to get true episode counts, since every cost figure scales directly off it.

1

Ingest — Tier 1 — built

~1 day
  • Feed parser (feedparser) → normalize both shows into episodes. Idempotent upsert on guid so re-runs are safe and cheap.
  • Strip HTML into description_text while keeping description_html — the hyperlinks in show notes are a genuine signal about who the guest is, worth not discarding.
  • FTS5 table + triggers to keep the index in sync on insert/update.
  • CLI: python -m app.ingest --backfill and --since.

Deliverable: a populated .sqlite with the entire archive of both shows, keyword-searchable from the shell. Real, useful, and it makes everything after it verifiable.

2

AI extraction — Tier 2 — the one piece still outstanding

~1–2 days
  • Batched extraction pass (Claude Haiku) over descriptions → structured guests, hosts, organizations, topics. Force JSON output against a fixed schema; store raw model output alongside parsed rows so a prompt change can be re-run without re-paying.
  • Entity resolution into people/topics via normalized_name, with a review CLI that lists near-duplicate names for a human call. Chris is the right person to sanity-check this once.
  • Seed the topic vocabulary from LHF's own language if they have one, rather than letting the model invent a taxonomy — otherwise you get "labor history," "Labor History," and "history of labor" as three topics.
3

Search API + internal UI — built, on stdlib not FastAPI

~2–3 days
  • FastAPI: /search?q=&person=&topic=&show=&year=, /episode/{id}, /people, /topics. FTS5 with bm25() ranking and snippet() for result excerpts.
  • Dark-mode UI, single search bar, filter chips, result cards linking out to Podbean. Server-rendered templates are entirely sufficient here — this doesn't need a SPA.
  • "In the can" flag + internal notes on episodes, behind a shared password.

This is the first build that's demoable to Harold and Chris, and it's the one that solves their stated problem. Worth getting in front of them before touching transcription.

4

Transcription — Tier 3 — mostly unnecessary; 144 came free

~2 days + backfill runtime
  • Worker loop per episode: download MP3 to scratch → upload to gs://…/audio/ → BatchRecognize → poll the long-running operation → parse results out of gs://…/transcripts/ → write segments + transcript_text → delete both the local file and the GCS object.
  • transcript_status state machine (pending → uploaded → processing → done | failed) so a crash resumes cleanly and one bad episode doesn't halt the run. Cap retries so a corrupt file can't loop forever.
  • Batch several files per BatchRecognize request, and run the first wave as ~20 episodes to confirm real spend against the estimate before turning it loose on the archive.
  • Throttle it. One or two episodes in flight at a time with a pause between — the box shares its uplink with everything else Coolify is running (see sizing above). Slow is free here.
  • Extend FTS to transcripts; add ?t= deep-links into the Podbean player from segment offsets.

The server does almost nothing here — it downloads, uploads, and writes down results. No model, no GPU, no sustained CPU load.

Then the second pass: once transcripts exist, re-run the Phase 2 extraction with the transcript in context alongside the show notes, via the Batch API. This is where guests who were never written into the notes finally get caught, and where AI-written summaries and segment-level topics come from. Keep the raw model output so a better prompt can be re-run later without re-transcribing.

5

Public widget + automation — automation built; widget and alerting not

~2 days
  • Read-only public search endpoint, rate-limited, no internal fields exposed. Embed as an iframe on laborheritage.org — simplest thing that survives whatever their site is built on.
  • Built — refresh.py runs the whole pipeline in order, with --loop 24h and exponential backoff. The ordering that used to be easy to get wrong is now impossible to get wrong.
  • Failure notification, even if it's just an email on exception. A silent broken cron is how this quietly rots in six months. Still outstanding — it logs to stderr, and nobody watches stderr.
  • The ?q= deep link means laborheritage.org can already link into a search from its own box; the styled embed is polish rather than plumbing.
Deployment

Docker + Coolify

Single image, two entrypoints — web and worker — sharing one volume. Nothing here needs orchestration beyond that. This is what shipped; the earlier sketch on this page assumed FastAPI and a local Whisper worker, and neither exists — the app is Python standard library only, and the transcripts came free from the feed.

services:
  web:
    build: .
    command: ["serve"]              # builds the DB on first run, then serves
    ports:
      - "8000:8000"
    volumes:
      - lhf-data:/data              # SQLite lives here
    environment:
      DATABASE_PATH: /data/lhf.sqlite
      LHF_HOST: 0.0.0.0             # a loopback bind is unreachable behind a proxy
      PORT: 8000
    restart: unless-stopped

  refresh:
    build: .
    command: ["refresh"]            # polls the feeds daily, then sleeps
    volumes:
      - lhf-data:/data
    environment:
      DATABASE_PATH: /data/lhf.sqlite
    restart: unless-stopped
    depends_on:
      - web                         # web creates the DB; this one waits for it

volumes:
  lhf-data:
  • No model volume, no API keys, nothing to install. The one dependency is the Python interpreter. What this section originally budgeted for — 1.5 GB of Whisper weights, a scratch volume for MP3s in flight — never became necessary.
  • The first deploy is the one that surprises you. The volume starts empty, so the container creates an empty database, starts serving in about a second, and fetches the archive in the background (~143s). Building it before serving is the obvious design and it does not deploy: nothing is listening during the build, so the health check fails, the orchestrator restarts the container as unhealthy, and the build starts over. We shipped that version first and Coolify rejected it in 55 seconds.
  • Coolify runs its own health check, ignoring the Dockerfile's, and shells out to curl — which python:3.12-slim does not have. Set Ports Exposes to 8000 (it defaults to 3000) and keep curl in the image.
  • SQLite on a volume: WAL mode is on, which is what makes one writer (refresh) and one reader (web) safe on the same file. Both containers must mount the same volume.
  • Sizing: both containers are tiny — 512 MB each is plenty. There is no transcription process to feed. The clip editor and waveform decoding all happen in the visitor's browser, so traffic costs this box almost nothing.
  • Backups: sqlite3 .backup on a schedule to a second volume path. The database is rebuildable from the feeds, but transcripts cost days of CPU to regenerate — those are the bytes worth protecting.
  • Secrets: only the Anthropic key on the local path. If we fall back to Google, its JSON goes in as a Coolify file mount — never in the image, never in git. Put secrets/ in .gitignore on day one, before any key exists locally.
Watch out for

Known risks

  • Extraction quality is the whole product. If guest names come out wrong or fragmented, the catalog is worse than useless — it's misleading. Hence the Phase 0 spike and a human review pass before anything ships.
  • Podbean pagination. The feed returns 100 items; the real archive is bigger. Confirm the true count before quoting timelines or costs.
  • Encore episodes. Both shows re-air material — the feeds are full of "(Encore)". Worth detecting and linking re-airs to originals, since "have we run this already" is literally the client's stated problem.
  • Audio URL rot. Store the Podbean episode page URL as well as the direct audio URL; the latter is likelier to change out from under us.
  • Proper-noun accuracy on local Whisper. The single biggest unknown, and the one the spike exists to answer. A transcript that renders "Elise Bryant" three different ways is worse than no transcript, because search silently fails and nobody can tell.
  • The backfill quietly dying. A two-week unattended job needs to log progress somewhere you'll actually look, or you find out on day twelve that it stopped on day two.
  • Scope creep toward Tier 4. Semantic search is fun and is not what they asked for. Ship 1–3 and let them use it first.
