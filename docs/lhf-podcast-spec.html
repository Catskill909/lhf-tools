Short answer

Yes — this is doable. Both shows already publish standard podcast RSS feeds with episode audio, descriptions, and dates, so the raw material is all there and machine-readable. The one real gap is that guest names and topics live inside free-text show notes rather than in their own fields, so the system needs a small amount of AI-assisted extraction, not just scraping. Full-text search on that data is straightforward at this scale.

What follows is a tiered build path — from plain scraping up to full AI — so you can see the options and decide how far you want to go. Nothing here commits you to the most ambitious version.

What's actually there

Feed audit

I pulled both feeds directly to see what we'd really be working with before speccing anything:

  • Labor Heritage Power Hour — weekly WPFW broadcast, archived at feed.podbean.com/yourrightsatwork/feed.xml. Averages ~55 minutes per episode. Hosted by Chris Garlock and Elise Bryant.
  • Labor History Today — weekly, archived at feed.podbean.com/laborhistorytoday/feed.xml. Averages ~30 minutes per episode.
  • Both feeds are standard iTunes-tagged RSS: title, publish date, duration, description, and a direct audio file link per episode. Fully machine-readable, no scraping-the-webpage required.
  • The catch: guest names and topics aren't separate fields — they're written into the description paragraph (e.g. "we hear from songwriter Mindy Murray about her powerful song…"). Sometimes the guest's name is hyperlinked, which helps, but there's no consistent pattern a simple program could rely on. This is why the system needs an AI reading step, not just a feed reader.
  • Podbean paginates at 100 items per request with a "load more" beyond that — so the true historical backlog on each show is larger than what a single fetch returns. Worth getting an exact count from Podbean's dashboard before scoping the backfill.
Roadmap

A tiered path — plain scraping up to full AI

"AI" gets used loosely, so here's the project broken into four tiers, stacked in order of how much AI is actually doing the work and what it costs to run. Each tier is a complete, usable tool on its own — you're not committing to Tier 4 by starting at Tier 1, and you could stop at any tier and pick the rest up later.

1

Basic Archive

No AI

What it does — pulls both podcast feeds and stores every episode's title, date, description, and audio link exactly as published. A search box runs plain keyword matching over that stored text.

What you get — instant search across whatever words already appear in the show notes. Type "Mindy Murray" and you'll find her episode, because her name happens to be in the text.

What you don't get — no real "browse by guest" or "browse by topic" list — just keyword luck. Two episodes about the same guest aren't linked unless the text matches. Nothing from the audio itself.

How it's built — an RSS feed reader plus SQLite full-text search. Ordinary software, zero AI, zero per-episode cost.

2

AI-Organized Catalog

AI reads the text

What it does — takes everything Tier 1 already scraped and adds one step: an AI model reads each episode's description and organizes it — who the guest was, who hosted, what topics or themes came up — instead of a person leaving that text as an unsorted paragraph.

What you get — real "browse by guest" and "browse by topic" pages, and search that understands "who's been on the show" as a question, not just a lucky keyword match.

What you don't get — anything from the audio itself. If a guest is never mentioned in the written show notes, this tier still can't find them.

How it's built — adds a single AI (language model) pass over text that's already been scraped — no audio involved, so the cost is a fraction of a cent per episode, not worth its own line item.

3

AI Transcription

AI listens to the audio

What it does — sends every episode's actual audio file through an AI speech-to-text engine, turning what was said on air into searchable text — not just the written summary of it.

What you get — search for a phrase someone actually spoke, and jump straight to that timestamp in the episode. Solves cases where a guest or topic was discussed but never written into the show notes.

What you don't get — automatic attribution of who said what (that's Tier 4) — the transcript is searchable, but not yet speaker-labeled by default.

How it's built — Google Cloud Speech-to-Text, run once per episode. This is the first tier that touches audio, and the only one with a real per-episode dollar cost — see the speech-to-text breakdown below (roughly 12–22¢ per episode).

4

Full AI Discovery

AI, advanced

What it does — layers smarter AI on top of the Tier 3 transcripts: natural-language search (find episodes about "1930s strikes" even if that exact phrase is never spoken), automatic speaker labeling so a quote is attributed to the right guest, AI-written episode summaries, and "more like this" suggestions on the public widget.

What you get — the "discovery engine" version of the tool — search by meaning, not just matching words.

How it's built — semantic (embeddings-based) search plus speaker diarization, layered on everything from Tiers 1–3.

The public widget for laborheritage.org doesn't need to wait for Tier 3 or 4 — it can launch as soon as Tier 2 is stable and just gets better as later tiers are layered in underneath it.

Naming

What do we actually call this?

There are a few industry terms for a system like this, and they're worth sorting out now, because each one sets a different expectation about what the tool does. They aren't competing options so much as descriptions of different tiers of the same project:

Podcast Metadata Scraper & Cataloger Describes Tiers 1–2

Accurate for the ingestion + extraction pipeline itself — the unglamorous part that pulls episodes and figures out who's in them.

Podcast Search & Indexing Engine Describes the backend, once search ships

The right technical name for the RSS-ingest + full-text-search system once the search box exists — Tier 2's endpoint.

Podcast Knowledge Base / Discovery Engine Describes where this is headed — recommended framing

This is the name I'd use with the board or on the website, because it's honest about the destination: once transcripts and AI search land in Tiers 3–4, people are searching what was said, not just what was written about an episode. It also doesn't over-promise on day one.

Audio Asset Management System / DAM Overkill for this scope

That term implies enterprise rights management, versioned masters, multi-department workflows. LHF has two shows and a clear use case — a DAM framing would push toward over-building.

Working name for the project itself: LHF Podcast Archive (public-facing, plain-language), with Podcast Knowledge Base as the internal name once the later tiers are in place.

Scope

Two audiences, one database

Everything you described — internal lookup for "did we already run this," and a public search box on laborheritage.org — is the same underlying data with two different front doors:

  • Internal tool (you, Chris, staff): full search with filters by guest, topic, host, air date; a way to flag an episode or segment as already re-aired ("in the can"); no public auth needed, just a shared link or simple password gate.
  • Public widget (laborheritage.org): a single search box embedded on a page, returning episode title, date, guest/topic tags, and a direct link out to the Podbean episode player. Read-only, no login, built to be dropped into the existing site as an iframe or small JS embed.

Storage

SQLite with an FTS5 virtual table is genuinely the right tool here, not a compromise — even a full backlog across both shows (low thousands of episodes) is a trivial dataset for it, and it means no separate search server to run or pay for. One .sqlite file on a Coolify volume holds episodes, extracted people/topics, and transcripts.

Reading the show notes

A small, inexpensive AI model reads each episode's description and pulls the useful pieces out of the prose — guest names, interviewer, organizations, topics — filing them into proper database fields so they can be browsed and filtered. The original text is kept and stays searchable alongside it, so nothing is lost in translation. Since it's only reading a paragraph or two per episode, this runs at fractions of a cent apiece.

Frontend

Dark-mode-first, Material-influenced, single search bar with filter chips (guest / topic / host / show / year). Same component library powers both the internal tool and the public widget — the public one is just a stripped-down, read-only view.

Speech-to-text

Should we transcribe every episode?

Show notes alone get you guest and topic search from day one (Tier 2). Full transcription is what lets someone search for a phrase actually spoken on air and jump to that exact moment — the more ambitious "discovery engine" version (Tier 3).

What "transcription" means here: not a person typing up episodes — an AI speech-to-text engine that listens to each episode's audio file and produces the text automatically, billed per minute of audio it processes. I've priced this against Google Cloud Speech-to-Text, in its batch mode: since we're working through a back catalog rather than transcribing live radio, results don't need to come back instantly, and that batch tier runs about 4x cheaper than Google's real-time pricing (~$0.004/min vs. ~$0.016/min, as of August 2026).

That per-minute rate translates to a flat per-episode cost, since each show runs a fairly consistent length:

Why Google over OpenAI or Groq: pricing lands in the same range as OpenAI's transcription models (~$0.006/min) and Google's batch tier includes built-in speaker diarization, which is genuinely useful here — it can separate host voices from guest voices automatically, which is most of the way to auto-attributing quotes to the right person. Groq's Whisper endpoint is cheaper still (~$0.0007/min) but at this scale the difference is a few dollars total, not worth adding a second vendor for.

Worth knowing: transcription doesn't have to be decided up front. The audio stays where it is on Podbean, so episodes can be run through speech-to-text at any point — all at once, gradually, or only for the years you care most about — without rebuilding anything underneath.

Infrastructure

What it runs on

Technical detail, included for the record — the practical takeaway is that this is a small, cheap thing to host, and nothing about it requires specialist hardware.

Because the transcription work happens on Google's servers rather than ours, the app itself stays lightweight: no graphics hardware, no heavy machine needed just to keep up with speech recognition.

  • Steady state (search + occasional ingest): 1 vCPU / 512MB–1GB RAM is comfortable. SQLite + FTS5 barely register at this data volume.
  • Backfill runs (bulk transcription pass): the server stays idle — the work happens on Google's side; our container is just sending files and writing down results, so no extra capacity is needed even during a big batch job.
  • Storage: one volume for the database file, plus a small scratch space for holding audio while it's being sent for transcription (cleared afterward — no need to keep local copies of the audio).
  • Deploy: a single container holding the search API, the feed ingest worker, and the scheduled job that checks both feeds for new episodes — deployed on the same self-hosted setup I already run for other projects, so there's no new platform for LHF to buy or maintain.
